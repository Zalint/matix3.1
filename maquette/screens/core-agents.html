Règles du registre

Core §7.2 · §10.2 · Technique §10 · Finance §9.3
  • À la demande uniquement. Chaque agent est interrogé uniquement à la demande explicite d'un utilisateur ; aucun écran ne déclenche d'appel automatique en arrière-plan (chargement de dashboard, rafraîchissement de KPI).
  • Droits effectifs = droits de l'agent ∩ droits du profil utilisateur. Les règles de sensibilité, validation et audit restent applicables ; Hautement sensible : restrictions possibles pour les agents IA (§5.3).
  • Budget mensuel plafond. Au-delà du plafond, l'agent cesse de répondre jusqu'au mois suivant ou jusqu'à relèvement explicite par un utilisateur autorisé.
  • Override temporaire. Un modèle plus coûteux peut être choisi pour une requête ou une période limitée ; l'override est audité, expire automatiquement et revient au routage par défaut ; le plafond reste applicable sauf relèvement explicite.
  • Sobriété V1. Aucun agent n'exploite de base vectorielle dédiée, ni d'indexation sémantique globale, ni de conservation massive des conversations pour créer une mémoire implicite ; seules les traces nécessaires à l'audit et les données explicitement utiles sont conservées (Technique §10).
  • Principe : si une règle déterministe suffit, ne pas utiliser l'IA. Le routage privilégie par défaut le modèle répondant au besoin au coût le plus faible.
  • Création guidée, modèle proposé, remplacement à deux validations. Décision de périmètre V1, hors cahier : l'agent n'est plus configuré librement. Le besoin est décrit en français, rapproché de la grille « types de tâches → modèles » tenue dans les Paramètres, et le modèle le moins cher capable de la tâche est proposé ; le remplacer demande deux détenteurs de core.agents.budget, distincts de l'initiateur et distincts entre eux, l'agent restant inactif jusqu'à la seconde validation. Dans la matrice de démonstration, seul le profil Super Admin détient cette permission (FIXTURES §2) : la seconde validation ne peut donc pas être acquise tant qu'un second détenteur n'est pas désigné.
  • Écriture encadrée. Un agent ayant des droits d'écriture doit passer en Test/Recette avant Production ; le Conseiller financier ne modifie pas directement les écritures financières et ne dispose pas d'une console SQL utilisateur (Finance §9.3).
Compromis assumé (Technique §10) : sans base vectorielle ni indexation sémantique, un agent ne peut pas retrouver rapidement des situations passées similaires par recherche floue ; il raisonne sur les données structurées interrogées à la demande. Acceptable au volume actuel ; à revisiter explicitement, agent par agent, si l'usage évolue.

Comment ça marche : Agents IA

Ce registre centralise tous les agents IA de l'ERP : les profils autorisés (permission core.agents.budget / core.agents.override) y créent un agent par un parcours guidé, fixent son budget, l'activent ou relèvent temporairement son modèle ; les autres profils le consultent en lecture.
  • Deux catégories, mais création en lecture seule. Le registre distingue Conseiller (consulte, recommande, jamais d'écriture directe) et Exécutant (uniquement les actions explicitement autorisées) : 2 Conseillers et 1 Exécutant sur 3 agents ; AG-02, seul Exécutant, reste en Test / Recette avant Production et n'a pas de console SQL (§7.2, Finance §9.3). Un agent IA étant une API de lecture uniquement bornée au périmètre de l'utilisateur, le parcours de création ne produit que des Conseillers en lecture (§7.2, §10.2).
  • Interrogation à la demande uniquement. Aucun agent n'est appelé automatiquement par un écran (dashboard, rafraîchissement de KPI) : le compteur « Requêtes déclenchées par un écran » reste à 0 (§7.2).
  • Le besoin est décrit, l'application propose le modèle. Décision de périmètre V1, hors cahier : au lieu de configurer l'agent librement, on écrit en français ce qu'il doit faire. L'application rapproche cette phrase de la grille « types de tâches → modèles » tenue dans les Paramètres et modifiable sans redéploiement, puis propose le modèle le moins cher capable de la tâche, en montrant le type reconnu, la capacité requise et le rang de coût. Aucun modèle n'est appelé pour cette analyse ; la liste des modèles et leurs coûts viennent de Mata Core.
  • Remplacer le modèle proposé demande deux validations. Décision de périmètre V1, hors cahier : si l'on retient un autre modèle que celui proposé, deux détenteurs de core.agents.budget, distincts de l'initiateur et distincts l'un de l'autre, doivent valider. L'agent est créé Inactif et le reste tant que la deuxième validation n'est pas acquise. Dans la matrice de démonstration, seul le Super Admin détient cette permission (FIXTURES §2) : le parcours montre les deux refus (initiateur, permission absente) mais ne peut pas aller jusqu'à la seconde validation.
  • Budget mensuel plafond. Au-delà de son plafond, un agent cesse de répondre jusqu'au mois suivant ou jusqu'à relèvement explicite. AG-01 a consommé sur en août, soit 62 % (§7.2).
  • Droits effectifs = droits de l'agent ∩ droits du profil utilisateur. La ligne « Droits effectifs pour vous » de chaque carte recalcule ce croisement pour le profil actif ; sensibilité, validation et audit restent applicables (§10.2).
  • Override temporaire de modèle. Un utilisateur autorisé force un modèle plus coûteux pour une requête ou une durée limitée ; le retour au modèle par défaut est automatique. 1 override est actif : AG-01, modèle avancé, jusqu'au 27/08 · 18:00 (Technique §10).
Refus par défaut et séparation des rôles : « Nouvel agent », le champ budget, le bouton d'override et le bouton « Valider le remplacement » restent visibles mais désactivés avec leur motif — permission absente, initiateur qui validerait sa propre demande, ou validateur déjà compté dans la première validation. Jamais masqués sans explication.
